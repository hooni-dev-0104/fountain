# 활동 원장과 전체 백업 v4

활동 원장은 서버가 확인한 콘텐츠 생성·편집·관리·삭제·열람 사실을 비공개로 기록한다. 법적 보류에 필요한 행위자와 콘텐츠 세대의 기반이며, 보류된 원문이나 첨부를 보존하는 기능은 아직 아니다. Notion의 [법적 보류 공개 요구사항](https://www.notion.com/help/legal-holds)을 참고했으며, 이 구현은 Notion 서버 내부 구조를 확인했다는 주장이 아니다.

## 기록 범위

페이지·데이터베이스·행의 변경을 실제 변경 전후 원문과 최종 콘텐츠 세대로 분류한다. 작성 필드가 바뀌면 `edited`, 이동·권한 등 다른 의미 있는 변경은 `managed`로 기록한다. 같은 값의 재저장과 시각·revision만 달라진 변경은 새 사실을 만들지 않는다. 보존 저장소 이동·해제와 신뢰된 전체 복원은 과거 자료를 새로 작성한 행위로 기록하지 않는다.

원장은 수집을 시작한 시점과 범위를 명시한다. 기존 감사 로그, 작성자, 생성 시각으로 과거 사건을 만들어 넣지 않는다. 사건은 커밋 후 변경할 수 없으며, 수집 구간별 순번과 명령 ID·순서로 중복을 검증한다. 서버의 새 인증 확인, 권한 검사, revision 충돌 검사, 명령 영수증과 같은 트랜잭션에서 커밋한다. 자동화·시스템·공개 폼은 출처를 구분하고 사람의 로그인으로 표시하지 않는다.

현재 열람 기록은 권한을 통과한 **직접 페이지 GET**과 명시적 공동편집 `open_command`에 적용된다. 같은 열기 명령 재전송은 한 번만 기록한다. HEAD, 워크스페이스 조회와 백그라운드 공동편집 폴링은 열람을 만들지 않는다. 데이터베이스·행 화면의 열람 연결과 오프라인 열람의 과거 시각 반영은 구현하지 않았다. 임의의 관리자 SQL은 `canonical-server-v1` 수집 범위 밖이다.

## 행위자와 원문 식별

멤버의 참여 구간과 인증 계정의 연결 구간을 분리한다. 역할·이름·이메일 변경이나 비밀번호 재설정은 같은 참여 구간을 유지한다. 탈퇴·비활성 뒤 복귀하면 새 참여 구간을 만들고, 비밀번호 인증 또는 Supabase 계정 연결을 해제했다가 다시 연결하면 해당 인증 구간만 새로 만든다. 두 인증 방식은 동시에 존재할 수 있다. 이 구간은 관리자 권한 세대와 별개다.

사건에는 정규화한 원문의 UTF-8 크기와 SHA-256, 콘텐츠 세대가 들어간다. Python과 PostgreSQL은 `fountain-cjson-v1`의 동일한 숫자·문자열·키 정렬 규칙을 사용한다. 이 해시는 원문 식별용이며 과거 본문이나 첨부 바이트의 스냅샷이 아니다. 현재 자료가 바뀐 뒤에도 과거 자료를 꺼내려면 별도의 보류 스냅샷과 첨부 핀이 필요하다.

비밀번호·토큰·세션 ID·실제 Supabase Auth 식별자와 현재 계정 연결 포인터는 휴대용 원장에 넣지 않는다. 비공개 테이블 7개는 강제 RLS를 사용하며 클라이언트의 직접 접근을 차단한다.

## 휴대용 형식과 복원

활동 자료가 있으면 전체 백업은 **v4 SQLite의 실제 테이블 14개**를 포함한다. 기존 콘텐츠·보존 테이블 10개와 다음 활동 테이블 4개다.

| 테이블 | 내용 |
| --- | --- |
| `activity_ledgers` | 수집 시작·복원 구간과 수집 범위 |
| `activity_memberships` | 멤버 참여 구간 |
| `activity_accounts` | 참여 구간 안의 인증 방식별 연결 구간 |
| `activity_events` | 변경할 수 없는 활동 사실과 원문 해시 |

현재 구간·순번·계정 연결을 결정하는 런타임 테이블 3개는 제외한다. 재개형 백업의 내부 정렬 자료도 결과 파일의 테이블이 아니다. 보존 자료가 비어 있어도 활동 자료가 있으면 v4의 보존 테이블을 함께 포함한다. 활동 자료가 없는 v1·v2·v3 형식은 기존 의미를 유지한다.

전체 복원은 스키마·참조·순번·원문 식별·첨부 바이트를 검증한 뒤 새 수집 구간을 시작한다. 과거의 열린 참여·인증 구간은 복원 사유로 닫고 이전 런타임 권한을 되살리지 않는다. 일반 시작이나 JSON 가져오기로 휴대용 과거 자료를 활성화할 수 없다. 재개형 작업은 열람과 인증 구간 종료를 포함한 모든 휴대용 활동 변경을 감지하여 서로 다른 시점의 자료가 섞이지 않게 한다.

## 적용과 검증

Supabase API **27**, 새 마이그레이션 **4개**에 반영했다. 누적 마이그레이션은 44개다. 배포 소스 48개와 원격 함수 본문 33개를 다시 읽어 비교했다. 검증 배포 103과 운영 배포가 공유하는 소스 46개도 같았다.

- 전체 Python 검사 **802개 통과**, 오류·실패·건너뜀 0개. 실제 PostgreSQL 설정에서 실행했고 이관·혼합 첨부 백업 검사도 포함한다.
- Node **74개 스크립트 통과**. v1~v3 호환, v4 양쪽 writer, 실제 SQL 응답, 재개와 변경 감지, 명시적 열람을 검사했다. TypeScript 정적 컴파일러는 없어서 정적 타입 검사는 실행하지 않았고 새 의존성도 설치하지 않았다.
- 실제 GoTrue 계정 2개와 Edge·PostgreSQL·Storage로 12단계의 원장 7건을 비교했다. 무변경 저장·백그라운드 조회·권한 없는 열람은 추가 기록을 만들지 않았다. 일반 멤버의 변경과 전체 백업은 403으로 거절됐다.
- 임시 루프백 화면에서 실제 브라우저의 소유자 연결과 멤버의 읽기 전용 상태를 확인했다. 두 번의 정상 온라인 페이지 열람으로 원장 2건이 늘었다. 최종 원장은 10건이며 앞선 시험 화면의 열람 1건을 포함한다. 이는 공개 Vercel 브라우저 또는 설치 앱 다섯 플랫폼의 검증이 아니다.
- 실제 16KiB 첨부와 동기식·재개형 v4 백업을 내려받아 복원했다. 두 파일은 각각 **172,032바이트**, 원장 원시 행과 첨부 바이트는 정확히 같았다. 전체 논리 자료도 같지만 첨부 JSON 한 행의 공백 표현 때문에 두 파일 전체의 SHA-256은 다르다.
- 시험용 단위 범위 113개와 실제 QA 범위 1개, 계정·세션·Storage 객체·작업 자료를 정리하고 SQL로 0건을 확인했다. 원장 삭제 예외는 해당 범위에 한정한 한 트랜잭션 안에서만 사용하고 원래 방어 함수 본문을 커밋 전에 복구했다. 전역 트리거 비활성화나 권한 부여는 하지 않았다. 검증 함수는 소스까지 확인한 **105**로 교체하여 모든 경로가 404를 반환한다.

원본 콘텐츠 153개·메타데이터 6개·계정 매핑 0개의 개수와 fingerprint를 다시 비교해 이전 값과 같은 것을 확인했다. 공개 웹과 로컬 8787의 앱 자산 해시는 기존 값과 일치했다. 기존 내부 테이블 24개의 RLS 기본 거부 안내와 `pg_net`의 public 스키마 경고는 남아 있으며, 확장은 이번에 옮기지 않았다. [확장 스키마 진단 설명](https://supabase.com/docs/guides/database/database-linter?lint=0014_extension_in_public)을 참고할 수 있다.

## 남은 범위

법적 보류 스냅샷·첨부 핀, 조직 소유자와 여러 워크스페이스, 지속 AI 대화의 수명 주기, 보존 정책·유지보수 권한, 관리자 보존 검색·검토 화면과 실제 사용자·가족의 다섯 플랫폼 여정은 남아 있다. 이번 검증은 5GB v4 백업이나 동시 부하 성능 검증도 포함하지 않는다. 기능 목록 41개의 전체 검증 완료 수는 여전히 0개이며 목표는 진행 중이다.

공개 근거 요약은 [활동 원장 검증 기록](research/activity-ledger-evidence.json)에 남겼다.
