# 비공개 보존 저장소 기반

이 구현은 휴지통 다음 단계에 필요한 저장소와 전체 백업의 기반이다. 자동 보관·영구 삭제, 관리자 보존 검색 화면, 법적 보류는 아직 활성화하지 않는다. 이 문서의 내부 커널을 공개 복원 API로 연결해서는 안 된다.

## 이동과 복구

`RetentionVault.archive_page`는 휴지통의 루트 페이지와 그 아래 페이지·데이터베이스·행, 버전·댓글·공동편집 상태와 관련 게시·폼·자동화 자료를 하나의 트랜잭션에서 옮긴다. 원본 JSON과 생성·수정 시각, 콘텐츠 세대와 작성·편집 이력을 유지한다. 보존 자료는 일반 콘텐츠 색인과 조회에서 빠지고, 옮긴 ID와 부모 연결은 재사용을 막는다. 외부 작업의 의존성 변경은 세대와 변경 전후 목록을 함께 기록한다.

첨부는 현재 화면뿐 아니라 공동편집의 현재 상태·기준 상태·실행 취소 이력에서 참조하는 파일까지 포함한다. 다른 일반 문서가 사용하는 첨부는 일반 저장소에 유지하면서 보존 기록에도 참조를 둔다. 파일·BLOB·클라우드 객체의 크기와 SHA-256 참조를 보호하며, 보존 중인 물리 파일은 정리 대상에서 제외한다. 완료하지 않은 업로드가 관련돼 있으면 먼저 완료하거나 취소해야 한다.

`restore_to_trash`는 **권한을 가진 내부 서버 코드가 전체 묶음을 해제하는 연산**이다. 루트 페이지는 휴지통 상태로 남지만, 자식의 기존 독립 공유·활성 상태도 돌아오므로 일부 자식 자료는 즉시 읽힐 수 있다. 따라서 외부에 노출할 때는 전체 묶음의 권한과 공유 영향을 검토하고 루트 활성화까지 같은 트랜잭션에서 처리해야 한다. 보이지 않는 임시 복원 단계로 취급해서는 안 된다. 사이트와 폼은 게시를 끄고 자동화는 비활성 상태로 복구한다.

공유 첨부는 서로 다른 보존 기록을 어떤 순서로 복원하더라도 다른 기록의 참조를 유지한다. 현재 데이터·첨부·의존성 목록이 충돌하면 덮어쓰지 않고 전체 작업을 거절한다. 파일을 검증할 수 없거나 다른 클라우드의 원래 객체가 없으면 성공으로 처리하지 않는다.

## 신뢰할 수 있는 전체 백업

보존 기록이 있는 전체 백업은 기존 네 테이블과 보존 전용 여섯 테이블을 포함하는 v3 SQLite 형식이다. 외부 파일·클라우드 첨부도 검증한 실제 바이트를 논리 BLOB 청크로 포함한다. 원본의 외부 참조는 이력으로 유지하며, 복구 대상에 따라 실행에 필요한 저장소 메타데이터만 정규화할 수 있다. 첨부 바이트를 준비하지 않은 메타데이터 복원은 허용하지 않는다.

보존 자료가 없는 백업은 기존 v1·v2 형식을 계속 지원한다. 보존 기록을 지원하지 않는 경로는 명시적으로 실패해야 하며 이를 빼고 정상 백업이라고 표시해서는 안 된다. 일반 JSON 가져오기로 보존 상태·역사적 작성자·사적인 권한을 주입할 수 없다. 전체 백업 파일에는 사용자 데이터가 포함되므로 안전한 위치에 보관해야 한다.

복원 시 스키마와 참조, 소유 계층, 작성 이력, 첨부 배치·크기·해시를 검증한다. 백업 파일의 임의 트리거나 UDF는 실행하지 않는다. 운영 중인 SQLite 원본의 알려진 보존 방어 트리거만 정확히 확인한 뒤 복사본에서 제거하며, 휴대용 결과에는 트리거를 싣지 않는다.

## 남은 구현

휴지통 만료와 보존 기간 정책, Supabase 유지보수 실행 권한, 관리자 보존 검색·복원·삭제 화면, 법적 보류와 삭제 차단, 조직 범위와 DB 행의 수명 주기, 실제 사용자·가족의 다섯 플랫폼 여정은 별도 구현·검증이 필요하다. 저장소 커널과 백업만으로 Notion 유료 기능 전체 또는 보존 기능의 운영 완료를 뜻하지 않는다.

## 적용과 검증

Supabase API 25와 마이그레이션 3개에 반영했다. 일반 휴지통 복원과 별도로 동작하는 내부 기반이며 자동 보관·영구 삭제는 켜지 않았다. 새 테이블 6개의 강제 RLS와 클라이언트 권한 차단, 보존 함수 14개의 실행 권한, 원격 함수 본문을 확인했다.

- 전체 Python 검사 744개 통과, 건너뜀 0개. 새 파일 보호 검사 4개와 기존 파일 검사 17개를 포함한다.
- Node 7개 스크립트의 146개 검사 통과. 기존 v1·v2 결과, v3 양쪽 writer의 동일 바이트, 큰 문서와 잘못된 참조·PK·이력·핀을 검사했다.
- 실제 PostgreSQL에서 1,004개 객체와 1,003개 이력의 보존·이관, 혼합 BLOB/파일, 공유 첨부의 복원 순서, 커밋 후 사적 기록 변경 차단을 확인했다. 4MiB 파일 복원의 manifest 조회는 128회에서 1회로 줄었고 바이트가 일치했다.
- 실제 Auth 계정 2개로 일반 콘텐츠 API의 보존 자료 404, 일반 멤버의 전체 백업 403, 소유자의 동기식·재개형 v3 백업을 확인했다. 두 결과는 241,664바이트로 정확히 같았고, 실제 Storage 전체 다운로드와 신뢰할 수 있는 복원 후 원문·세대·이력·첨부·의존성 저널이 일치했다.
- 재개형 작업의 PostgreSQL 바이트 위치 타입 오류를 별도 마이그레이션으로 수정한 뒤 같은 작업을 이어 완료했다. 작은 시험 자료의 최대 단계는 3.557초·32 RPC였다. 이를 대용량·다중 사용자 성능 보장으로 확대하지 않는다.

시험 계정·세션·객체·워크스페이스 자료를 정리하고 검증 함수를 항상 404를 반환하는 버전 99로 교체했다. Supabase의 기존 원본 153개 객체·메타데이터 6개의 fingerprint와 공개 웹·8787 자산 바이트는 유지했다. 이번 변경에서 새 브라우저 UI나 설치 앱 여정, 5GB 보존 백업, TypeScript 정적 타입 검사는 실행하지 않았다. SQL의 클라우드 객체 확인은 경로·크기 메타데이터 검사이며 공급자 바이트 해시 검증이라고 표시하지 않는다.

Supabase 진단에는 기존 내부 작업 테이블 24개의 의도된 RLS 기본 거부 안내와 기존 `pg_net`의 public 스키마 경고가 남아 있다. 새 보존 테이블에는 이 안내가 발생하지 않았다. 확장은 이번 변경에서 옮기지 않았으며 [확장 스키마 진단 설명](https://supabase.com/docs/guides/database/database-linter?lint=0014_extension_in_public)을 따로 확인할 수 있다.

범위를 구분한 근거는 [보존·백업 검증 기록](research/retention-vault-evidence.json)에 남겼다.
