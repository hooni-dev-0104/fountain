# 데이터베이스 담당자와 검증

데이터베이스의 **속성 추가**에서 **담당자(Owner)** 또는 **검증(Verification)**을 선택한다. 검증 속성을 추가하면 연결할 담당자 속성도 자동으로 생긴다. 데이터베이스마다 각 유형은 하나씩 지원하며, 기존 일반 사람(`person`) 속성을 이름만으로 담당자 속성으로 바꾸지 않는다.

행의 상세 화면에서 담당자를 선택하고 **검증 설정 열기**로 만료일 지정·만료 없음·검증 해제를 사용한다. 표·카드·목록에는 담당자와 현재 검증 상태를 표시한다. 검증 창을 열어도 작성 중인 다른 행 속성은 유지한다. 화면·계정·권한이 바뀌면 이전 요청 결과를 다른 항목에 적용하지 않으며, 충돌 시 입력을 남기고 최신 상태 확인을 안내한다.

## 담당자와 권한

담당자는 그 행을 현재 볼 수 있는 활성 구성원이어야 한다. **지식 담당자 지정은 공유 권한을 추가하지 않는다.** 실제 생성자 `row.owner_id`, 기존 항목별 접근 제어에 쓰는 일반 사람 속성, 지식 담당자는 별개다. 일반 사람 속성을 담당자로 바꾸어 항목별 접근 권한을 우회할 수 없다.

검증과 해제에는 현재 행의 편집 이상 권한과 유효한 담당자 한 명 이상이 필요하다. 검증하는 편집자가 담당자 본인일 필요는 없다. 이는 지식 담당자 본인만 검증하는 [위키 자식 페이지](WIKI.md)와 다른 규칙이다. 게스트에게 숨겨진 담당자의 ID·이름·인원 수는 공개하지 않으며, 보이는 담당자를 편집할 때 기존의 숨겨진 유효한 담당자는 보존한다.

데이터베이스 전체 권한이 있는 사용자는 **담당자 속성 설정**에서 담당자 수를 **한 명 / 제한 없음**, 새 항목 기본값을 **작성자 / 기본값 없음**으로 선택한다. 요청당 담당자 ID는 중복 제거 전 최대 1,000개다. `제한 없음`도 이 기술적 요청 한도를 없애지는 않는다. 여러 담당자가 있는 상태에서 `한 명`으로 줄이면 409로 거절하며 임의로 사람을 제거하지 않는다.

## 기본값과 기록 보존

Fountain의 새 담당자 속성 기본 설정은 `limit: "one"`, `default: "created_by"`다. 속성을 활성화할 때의 기본값을 `initial_default`로 고정한다. 기존 행에 명시적인 담당자 값이 없으면 이 값과 유효한 기존 `row.owner_id`로 담당자를 해석하며, 행을 일괄 수정하거나 과거 생성자를 추정하지 않는다. 새 행에는 현재 기본값에 따라 실제 생성자 또는 빈 목록을 명시적으로 저장한다. 이후 기본값을 바꾸어도 이미 만들어진 행의 담당자는 바뀌지 않는다.

서버는 속성의 `generation`과 검증 회차를 관리한다. 검증 속성 제거 후 같은 ID로 다시 추가해도 과거 검증이 살아나지 않는다. 연결된 담당자 속성을 제거하려면 검증 속성도 함께 제거해야 하며, 검증만 제거하고 담당자를 남길 수 있다. 담당자 변경은 유효한 검증의 시각·만료일·검증자를 보존한다. 담당자가 모두 부적격해지면 검증된 항목으로 표시하지 않는다. 저장된 날짜가 잘못된 검증은 상태 확인 필요로 표시한다.

복제한 행은 새 생성자와 현재 기본값을 사용하고 검증 증거를 가져오지 않는다. JSON 가져오기는 기존의 모든 특수 담당자 값·검증 증거·서버 세대를 버리고, 새 생성자와 가져온 속성의 기본값으로 담당자를 다시 정한다. JSON 내보내기는 공개 데이터를 내보내므로 신뢰 기록을 복원하는 백업이 아니다. 전체 SQLite 백업은 별도의 원본 복원 경로다.

위 초기 설정·기존 행 해석·삭제 후 재추가·복제·가져오기 정책은 **Fountain의 독립 설계**다. Notion 서버에서 같은 정책을 관찰했다는 의미가 아니다.

## API와 동시 변경

| 요청 | 입력과 결과 |
| --- | --- |
| `GET /api/databases/{db}/rows/{row}/verification` | 현재 `revision`, 담당자·검증 속성 설정, 공개 담당자·검증 상태, 선택 가능한 `members`, `can_verify`, `can_manage`를 읽는다. |
| `POST /api/databases/{db}/rows/{row}/verification` | 필수 `revision`과 선택적 `expires_at`을 받는다. `null` 또는 생략은 무기한, 날짜는 시간대가 있는 미래 시각이다. |
| `DELETE /api/databases/{db}/rows/{row}/verification` | 필수 `revision`으로 검증을 해제한다. |

검증 API는 쿼리 매개변수를 받지 않으며 GET 본문과 알 수 없는 변경 필드는 거절한다. `revision`은 원본 행과 현재 속성 설정에서 계산한 소문자 64자리 16진수의 불투명 토큰이다. 누락·잘못된 형식은 400, 다른 변경이 먼저 저장된 경우는 409다. 토큰은 권한을 부여하지 않으며 서버가 같은 트랜잭션에서 접근 권한과 행·데이터베이스 연결을 다시 검사한다. 담당자 속성만 있으면 조회의 `verification_property`는 `null`이고, 담당자 속성도 없으면 404다.

검증 속성의 공개 값은 `status`, `owners`, `owner`, `verified_by`, `verified_at`, `expires_at`이다. 상태는 `unverified`, `verified`, `expired`, `unknown`이다. 비공개 검증 원본·회차·행의 담당자 세대는 공개 응답에서 제거하며 특수 속성을 모두 삭제한 뒤에도 노출하지 않는다.

데이터베이스 응답의 `schema_revision`도 불투명한 64자리 토큰이다. 속성을 바꾸는 `PATCH /api/databases/{db}`에 이 값을 보내면 같은 트랜잭션에서 400/409 검사를 수행한다. 이전 API 호출과의 호환을 위해 생략은 지원하지만 현재 화면은 최신 설정을 확인하고 항상 토큰을 보낸다. `generation`, `initial_default`, 연결 속성 ID는 서버가 관리하며 클라이언트가 변경할 수 없다.

## 다른 기능과 오프라인

담당자 값은 ID 배열이고 검증 값은 읽기 전용 계산 결과다. 검색·필터·정렬·수식·관계 대상별 롤업·자동화 조건·CSV는 현재 사용자의 공개 값으로 계산하여 숨겨진 담당자가 결과에 섞이지 않게 한다. 일반 행 변경·양식·가져오기·자동화로 검증 원본이나 계산 값을 지정할 수 없다. 양식은 특수 담당자와 검증 답변을 받지 않으며 새 응답 행의 담당자는 실제 생성자 기본값으로 정한다. 자동화의 담당자 변경도 실행 작성자의 현재 행 권한과 같은 검증 규칙을 적용한다.

담당자 편집은 기존 오프라인 대기열과 복구 경로를 사용한다. 다시 연결할 때 속성 유형·세대·기본값·편집 기준을 검사하고 숨겨진 유효한 담당자를 보존한다. 검증·해제와 속성 설정 변경은 서버 연결이 필요하며 자동 대기열에 넣지 않는다. 담당자는 [알림함](INBOX.md)에서 현재 만료된 행 검증과 개인별 읽음·보관 상태를 확인한다. 배경 만료 사건 저장·이메일·OS 푸시는 구현 범위에 포함되지 않는다.

## 근거와 검증 범위

[Notion 공식 안내](https://www.notion.com/help/wikis-and-verified-pages)에서 검증 추가 시 담당자 자동 추가, 편집자의 검증, 만료일·해제, 담당자 수와 기본값 설정을 확인했다. 설치 클라이언트의 [REA 조사](research/notion-desktop.md)는 선택한 파일에 대한 증거이며 비공개 데이터베이스 서버의 복원 결과가 아니다.

Python·TypeScript의 권한·형식·기본값·세대·동시 변경·롤백·파생 값·가져오기·복제·오프라인 경로와 실제 Chrome의 행 편집·화면 전환 경쟁·속성 충돌·390px 화면을 검사했다. 이번 전체 Python 검사는 실제 PostgreSQL을 연결해 579개가 skip 없이 통과했다. 격리된 Supabase 계정 검사에서는 두 계정·세 세션으로 스키마 자동 연결, 실제 생성자 기본값, 편집자 검증, 두 세션 충돌, 위조 거절, 게스트 가림, 양식·수동 자동화, 제거 후 재추가를 확인했다.

클라우드 알림함은 서버가 계산하는 `database_verification_rows_v1`의 제한된 데이터베이스·행 메타데이터를 사용한다. 관계없는 행의 일반 속성 본문을 읽는 방식으로 대체하지 않으며 기존 응답·트랜잭션 용량 한도는 유지한다. 이 메타데이터 변경은 migration `20261017063604`로 적용했으며 기존 SQL 함수 소유자·권한은 유지했다.

실제 worker 4의 예약 실행에서 담당자 변경·새 행 작성자 기본값·페이지 생성과 위조 작업의 원자적 롤백을 확인했다. 약 85.4MB의 행과 큰 검증 행을 넣은 실제 SQL·HTTP 검사에서 알림함은 본문을 읽지 않았고 개인 읽음·보관만 저장했다. 만료 시각은 운영자가 설정한 시험 값이며 실제 하루 경과를 기다린 증거는 아니다. [배포·정리·설치 증거](research/database-verification-evidence.json)를 참고한다.

이 증분은 DB 담당자·검증 구현의 검사 범위다. 운영 배포·예약 실행·정리 결과는 [클라우드 백엔드 상태](supabase-backend.md)를 따른다. TypeScript 컴파일러 정적 검사, 실제 Windows 실행·물리 모바일 기기, 실사용 가족 계정의 다섯 플랫폼 전체 여정과 모든 유료 기능 동등성은 별도 검증이 남아 있다.
