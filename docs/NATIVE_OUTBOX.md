# 모바일 SQLite 저장소

현재 iOS·Android의 기본 설정은 `outboxVersion: 1`, `outboxEnabled: true`이며
복구 기능도 활성화합니다. 네이티브가 SQLite COMMIT을 확인한 미전송 편집은
프로세스 재시작과 WebView IndexedDB 제거 뒤에도 같은 계정·로그인 범위의 현재 권한으로
다시 읽을 수 있습니다. IndexedDB는 화면 캐시와 저장 intent에도 사용하지만,
캐시에 기록됐다는 이유만으로 네이티브 저장 성공을 표시하지 않습니다.

기본 활성화 021 검증은 별도의 활성화 override 없이 실제 번들 bridge의 설정을
확인했습니다. 두 플랫폼에서 로그인·온라인 편집, 오프라인 편집 보관, 프로세스
재시작, IndexedDB 제거 뒤 복원, 재접속·전송·로그아웃의 5단계를 각각 다른
프로세스로 실행했습니다. 오프라인 두 단계의 HTTPS 전송은 0회였습니다.
[실행 결과와 범위](research/native-outbox-activation-verification.md) ·
[증거 목록](research/native-outbox-activation-verification.json)

이 보장은 **현재 로그인 범위에서 네이티브 COMMIT이 확인된 자료**에 해당합니다.
COMMIT 전의 미확인 입력과 다른 로그인 범위의 원문을 보존한 내부 IndexedDB
저널은 같은 보장이 없습니다. IndexedDB 제거 전에 서버 동기화나 복구 내보내기를
완료해야 하며, 앱 삭제·OS 저장소 초기화 뒤 로컬 자료 보존도 보장하지 않습니다.
서버에 저장한 자료는 같은 계정과 현재 권한으로 다시 받을 수 있습니다.

## 구현 경계

기존 실시간 문서의 ACK 처리는 canonical snapshot 저장과 확인된 대기 작업
삭제를 하나의 IndexedDB 트랜잭션으로 묶습니다. 선택된 저장 snapshot의
같은 epoch `state.seen`이 증명한 ID만 삭제합니다. 저장 실패 시 미전송 작업을
남기며, 메모리의 최신 상태만으로 디스크 저장을 추정하지 않습니다. 이 수정은
웹과 기존 모바일 캐시 경로에도 적용됩니다.

SQLite 기반은 iOS의 SQLite3, Android의 SQLiteDatabase를 사용하며 별도
SQLite 플러그인이나 새로운 인증 토큰을 추가하지 않습니다. OS 앱 전용 경로와
백업 제외를 사용하고, DELETE journal 및 EXTRA 동기화 설정을 확인합니다.
이는 앱 데이터의 별도 암호화나 물리적 완전 삭제를 보장한다는 의미가 아닙니다.
세션 쿠키와 자격 증명은 기존 네이티브 보안 저장소에만 남습니다.

기본 네이티브 어댑터는 다음 순서로 저장합니다.

1. 실제 IndexedDB 쓰기와 복구 intent를 같은 트랜잭션에 기록합니다.
2. 완료 후 변경분을 작은 조각으로 네이티브에 전송합니다.
3. SQLite COMMIT 성공 응답을 받은 뒤에만 호출자에게 저장 성공을 반환합니다.
4. 응답 유실 시 동일 txId와 digest로 receipt를 재확인합니다. 미확정 상태에서는
   기기 업무자료의 후속 읽기와 쓰기를 차단합니다.

로그인 grant는 네이티브가 실제 관측한 `/api/session` 응답에서만 얻습니다.
공개 profile을 JS에서 저장하는 것으로 grant를 만들 수 없습니다. 서버 origin,
작업공간, 멤버, 로그인 binding을 구분하고, 이전 로그인·문서의 tombstone은
늦은 응답으로 지울 수 없습니다. 파일 전송 상태와 publication receipt는
같은 폐기 범위에 포함하며 실제 파일 바이트는 여기에 저장하지 않습니다.

## 리소스 접근 검증 코드

네이티브가 실제로 받은 정규 GET 작업공간·문서 공동 편집·DB 응답과 성공한
문서 operations POST 응답으로 비공개 접근 자료를 기록합니다. 현재 계정·로그인 구분값과
쿠키 범위를 대조하며, 웹 화면에서 이 접근 자료를 만들어 넣을 수 없습니다.
검증 수명은 로그인 만료와 24시간 중 짧은 쪽입니다. 내용이 같은 반복 응답은
기한을 연장하지 않습니다. 별도의 검증 세대는 저장 이력과 구분합니다.

DB 담당자 변경은 행의 접근 범위를 바꿀 수 있으므로 접근 revision뿐 아니라
현재까지 확인한 데이터 revision도 적용합니다. 예전 DB 자료끼리 값이 맞더라도
더 최신 변경을 확인했다면 재검증 전에는 복원하지 않습니다. 로그인 자료 안의
중첩 작업공간·문서·DB와 이전 편집 기준의 관계 참조도 같은 검사를 받습니다.

복원할 자료 중 확인할 수 없는 항목이 있으면 첫 자료를 반환하기 전에 중단하고
기존 IndexedDB·SQLite·미전송 작업을 보존합니다. 새 저장도 원자적 트랜잭션
안에서 최종 자료를 검사합니다. 이미 저장된 동일 작업의 완료 응답 재확인은
원래 결과를 반환하므로 응답 유실을 중복 저장으로 처리하지 않습니다. 실제
리소스 접근 거절은 미전송 입력을 격리 보관한 뒤 활성 캐시를 제거합니다.
명시적 로그아웃은 해당 사용자의 네이티브 활성·격리 자료를 정리합니다.
격리 자료나 다른 로그인 범위의 입력을 새 계정에 자동 재생하지 않습니다.

네이티브 자료 읽기는 작은 조각으로 진행합니다. 비공개 접근 자료는 합계 16MiB,
개별 저장 레코드는 16MiB, 변경 묶음은 64MiB 기술 한도를 적용합니다. 다른 로그인의
기존 IndexedDB 원본을 보존할 때는 현재 캐시까지 포함한 DB별 전체 목록과 새 보존
기록을 합쳐 64MiB로 제한합니다. 보존 레코드의 16MiB 한도에는 포장 정보도 포함합니다.
초과하면 자료를 지우거나 잘라내지 않고 작업을 중단하며 원본을 유지합니다.

초기 리소스 접근 연구는 소스 검토·일반 SQLite·JDK와 실제 HTTP/Chrome/IndexedDB의
네이티브 모의 모델을 사용했습니다. 당시의 기본 비활성 상태와 검증 한계는
[초기 기록](research/native-resource-access-verification.json)에 그대로 남깁니다.
이 기록을 이후의 실제 SDK·기본 활성화 검증으로 해석하지 않습니다.

## 자료 재조정과 복구

현재 경로는 서버에서 새로 관측한 접근 자료로 캐시와 대기 작업을 재조정합니다.
로컬 새 페이지와 행의 의존성을 확인하고, 충돌한 입력은 활성 자료 교체 전에 보관합니다.
복구 자료를 새 변경으로 가져오려면 현재 계정의 권한과 선택 범위를 다시 확인하고
화면에서 명시적으로 승인해야 합니다. 읽기·파일 내보내기는
[기기 기록 복구](NATIVE_RECOVERY.md)를 따릅니다.
다른 로그인 binding의 자료를 자동 재전송하거나 이전 문서 snapshot을 그대로
활성 캐시로 승격해서는 안 됩니다.

응답이 유실된 저장 intent는 원래 txId·digest와 논리 범위를 유지한 채 실제 receipt를
확인합니다. 수락 여부를 확인하지 못하면 새 작업으로 다시 적용하거나 원본을 지우지
않습니다. 다른 로그인 범위의 저널은 네이티브에서 대신 처리하지 않습니다. 사용자가
최신 상태로 계속하기를 선택하면 원문을 내부 IndexedDB에 별도로 보존한 뒤 현재
계정의 정본을 읽습니다. 이 내부 보존은 네이티브 격리 완료나 서버 저장 증거가 아닙니다.

편집 POST 관찰의 선행 수정은 iOS Simulator·Android Emulator의 실제 SQLite
컴포넌트 검사로 검증했습니다. 합성 세션을 사용한 당시 검사는 기본 활성 bridge와
실제 계정의 전체 실행과 구분합니다.
[실행 근거와 남은 작업](research/native-operations-observer-verification.md).
사용자가 설치·설정을 마쳐 기존 Xcode 라이선스·Android SDK 미설치 장애는 해소됐습니다. 라이선스 자동 수락이나 TLS 검증 완화는 하지 않습니다.

## 실제 검증과 남은 범위

기본 활성화 검증은 격리된 QA 작업공간의 실제 Supabase 계정·DB를 사용했습니다.
iOS는 저장 표시와 별도의 네이티브 GET 200, 로그아웃과 대기 마커 정리를 확인했고,
Android도 저장 표시·실제 서버 재조회·대기 전송 후 로그아웃을 확인했습니다.
이 결과는 원본 작업공간의 실제 소유자 연결이나 전체 다섯 플랫폼 동시 전파를
검증한 것이 아닙니다.

별도 019/020 네이티브 컴포넌트 검사는 활성 COMMIT 전 SIGKILL과 수락·미수락
기록의 재시작 처리를 확인했습니다. 이 검사는 합성 인증을 사용하며 트랜잭션 도중
프로세스 종료, 전원 차단, 실제 계정 인증 중 강제 종료를 증명하지 않습니다.

현재 근거는 iOS Simulator와 Android Emulator에 한정합니다. 물리 기기, 전원 차단,
모든 저장 공간 부족 상황, 장시간 대용량 사용, 릴리스 서명·배포는 별도 검증이
필요합니다. Chrome·모의 bridge·일반 SQLite/JDK 검증도 각각의 범위를 유지하며
실제 SDK 실행의 대체 증거로 계산하지 않습니다.
