# 저장 버전 비교와 복원

페이지 오른쪽 위의 기록 버튼에서 저장된 버전을 선택합니다. 왼쪽은 선택한 이전 버전, 오른쪽은 기록을 열었을 때의 서버 내용입니다. 제목과 본문에서 없어진 부분은 빨강, 현재 추가된 부분은 초록으로 표시합니다. 블록 추가·삭제·이동과 서식·속성 변경도 구분합니다. 긴 텍스트는 달라진 구간을 묶어 표시합니다.

미리보기와 버전 선택은 문서를 바꾸지 않습니다. 첨부는 이름·크기만 표시하며 비교를 위해 파일을 다운로드하지 않습니다. 이력 본문을 오프라인 캐시에 따로 보관하지 않습니다. 기록 열기에는 서버 연결과 편집 이상 권한이 필요합니다.

**제목과 본문 복원**을 누르면 확인 화면을 먼저 표시합니다. 최종 확인은 전체 권한이 있고 잠금이 해제된 페이지에서만 가능합니다. 현재 제목·본문은 새 저장 버전으로 남으므로 다시 돌아갈 수 있습니다. 복원은 저장 버전의 제목·본문에만 적용하며 아이콘·표지·즐겨찾기·페이지 위치·공유 권한을 바꾸지 않습니다. 제목 기록이 없는 이전 형식의 버전은 현재 제목을 유지합니다.

기록을 연 뒤 다른 변경이 서버에 저장되면 복원을 중단합니다. **최신 기록 다시 열기**로 다시 비교한 뒤 확인하세요. 다른 페이지나 계정으로 이동하거나 권한·편집 epoch가 바뀌면 늦은 응답이 새 화면을 채우지 못하도록 처리합니다.

앱은 저장 버전에 보관 기한을 두지 않습니다. 실제 DB·디스크 용량은 필요하며 [Supabase 무료 인프라의 제약](SUPABASE.md)은 별개입니다. 현재는 페이지 제목·본문의 저장 시점 비교입니다. 버전 이름·북마크, 모든 변경의 작성자 표시, DB 전체 복원과 이력 페이지 나누기는 남아 있습니다.

## API와 구현

페이지 상세의 권한 있는 `versions`와 기존 복원 API를 사용합니다. 보기·댓글 권한에는 이전 본문을 전달하지 않습니다. UI의 복원 요청은 비교 시점의 현재 `revision`을 전송하고, 서버는 같은 쓰기 트랜잭션에서 현재 revision·페이지/버전 소속·잠금·삭제 상태·첨부 권한을 확인합니다.

```text
POST /api/pages/:page_id/versions/:version_id/restore
{"revision": 17}
```

다른 변경이 있으면 409이며 페이지·CRDT epoch·버전·감사 기록을 바꾸지 않습니다. 저장 실패도 전체 트랜잭션을 롤백합니다. 호환성을 위해 revision을 보내지 않는 기존 API 호출은 유지하므로 별도 클라이언트도 비교 후 복원하려면 반드시 revision을 전송해야 합니다.

비교기는 저장된 블록 ID와 공통 형제의 상대 순서로 이동을 판정합니다. 앞에 블록을 추가했다고 나머지 전부를 이동으로 표시하지 않습니다. 텍스트는 Unicode codepoint를 보존하고, 문서 전체 계산 예산을 넘으면 구간 단위 비교로 전환합니다. 기본 서식과 `bold:false` 같은 같은 표시 상태는 변경으로 세지 않습니다. Notion 서버의 비교 알고리즘을 복원한 코드는 아닙니다.

[Notion 공식 이력 안내](https://www.notion.com/help/duplicate-delete-and-restore-content)는 변경 강조·복원 미리보기·편집 이상 권한을 설명합니다. Fountain의 기존 전체 권한 복원 정책은 유지하며 웹·작은 화면의 자체 비교 UI를 제공합니다.

## 검증

```sh
node tests/version-diff.mjs
python3 -m unittest tests.test_version_restore
node tests/browser-versions.mjs
```

순수 비교 검증은 독립 예상값, 1,200개 재구성 사례, Unicode·이동·기본 서식 동등성, 4MiB 텍스트의 64MiB heap 제한을 포함합니다. HTTP 검증은 stale revision·두 서버 경쟁·정상/기존 호출·제목/본문과 메타데이터·실패 롤백을 검사합니다. Chrome은 임시 실제 서버에서 비교·복원·권한·계정과 화면 전환·지연 응답·XSS·모바일 레이아웃을 확인합니다. 실제 사용자 DB를 fixture로 사용하지 않습니다.

실제 Supabase의 서로 다른 두 서버에서도 오래된 revision 거절, 제목·본문 복원의 revision 1회 증가와 메타데이터 보존, 제목 저장 실패 시 private CRDT·이력·감사 카운터까지 전체 롤백하는 두 시나리오를 확인했습니다. 임시 namespace는 검증 후 삭제했습니다.
