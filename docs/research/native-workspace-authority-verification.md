# 모바일 문서 생성 권한 검증

2026-10-17에 workspace 응답의 가시적인 팀스페이스마다 현재 사용자의 `access_level`을 계산하도록 Python 기준 구현과 Supabase 구현을 맞췄다. 모바일이 문서 생성 권한을 자체 추정하지 않도록 하기 위한 변경이다. 필터링 뒤에 계산하며, 저장된 `access_level` 값은 권한 근거로 사용하지 않는다. 서버의 기존 ACL과 게스트 자식 문서 생성 규칙은 유지한다.

Supabase `fountain-api` version 12의 배포 SHA-256은 `2dce2f77a0e62712e4c6c66a75912b4a4052f13ff1b303d456b867c964f9ae17`이다. 배포 파일 39개를 다시 받아 요청한 내용과 일치함을 확인했다. 이전 배포와의 차이는 공통 authorization 모듈 하나이며, 기존 작업공간·웹 origin·setup 비활성 설정과 `ready:false`를 유지했다.

Python/SQLite 권한 검사 36개와 Node source 검사 383개가 통과했다. 독립 검토에서도 권한 상승이나 숨겨진 팀스페이스 노출 문제를 찾지 못했고, 별도로 새 Python 검사 2개와 Node domain 검사 6개를 재실행했다. TypeScript 전용 컴파일러 검사를 실행한 결과는 아니다.

격리한 실제 Supabase 계정 두 개로 소유자 수준 4·일반 구성원 수준 3을 확인했다. 명시적인 팀스페이스 구성원인 사용자를 게스트로 바꾼 경우에도 최상위 문서 생성은 403으로 거절했고, 편집 권한이 있는 부모 아래 자식 문서 생성은 201로 처리했다. 이후 일반 구성원 역할로 되돌렸다. 앱 UI에서 이 흐름이 동작한다는 증거와는 구분한다.

같은 격리 환경에서 실제 `/api/sync` 요청도 확인했다. 문서 생성·제목 수정·자식 문서 생성의 종속 관계가 적용됐고, 중복 생성 ID를 포함한 네 결과와 같은 배치 재시도는 동일한 의미의 영수증을 반환했다. 같은 ID의 본문 변경은 409 결과, 잘못된 로그인 binding은 HTTP 403으로 거절했다. 실제 canonical 문서 epoch와 최종 제목도 일치했다. JSONB에 저장한 영수증은 JSON 키 순서가 달라질 수 있으므로 비교는 의미 기준으로 수행했다. 이 검증은 네이티브 HTTP 관찰자나 앱 재시작 검증을 대신하지 않는다.

본 API의 익명·설정·origin 거절 경계 10개가 통과했고 기존 가족 작업공간 여섯 데이터 묶음의 지문도 동일했다. 이 단계는 전체 운영 전환 또는 모바일 내구성 저장의 활성화 완료를 뜻하지 않는다. 검증 계정과 임시 함수의 정리 상태는 [실행 기록](native-workspace-authority-verification.json)에 별도로 기록한다.
